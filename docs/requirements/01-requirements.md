# RentManager 要件定義書

版: 0.1（レビュー用ドラフト） / 作成日: 2026-09-23

対象リポジトリ: https://github.com/K-suk/rentmanager

## 1. 目的と成功条件

中小企業の備品貸出業務を題材に「このような業務アプリを作れるようになる」と伝える公開デモを作る。実在企業の業務運用ではなく、架空の社員・備品のみを扱う。AI機能は搭載しない。

成功条件:

1. 公開URLを別のPC・スマートフォンから開き、デモ社員としてログインできる。
2. 社員Aが借りた備品は、社員Bが一覧を再取得すると貸出中と表示され、二重に借りられない。
3. 貸出・延長・返却・履歴確認を完了でき、再ログインしてもデータが残る。
4. 管理者が備品と社員を管理し、代理返却できる。一般社員は管理操作を実行できない。
5. 期限超過・備品削除後の履歴・無効社員のアクセス拒否を再現できる。
6. PCとスマートフォンで主要操作が完了する。
7. 開発者用コマンドで、保護された初期管理者を維持しながらデモ初期状態に戻せる。

今日中にOrcaでの並列開発へ渡し、実装・公開まで進めることを目標とする。外部認証の接続や公開先の条件確認が未完了の場合、完了を保証する納期ではない。

## 2. 対象ユーザー・課題

| ユーザー | 課題・利用目的 |
|---|---|
| 一般社員（架空） | 空いている備品を探し、自分で借り、期限を確認して延長・返却する |
| 管理者（架空） | 備品と社員を管理し、全体の貸出状況・履歴を確認する |
| デモ閲覧者 | 複数の役割を試して、業務アプリで実現できることを理解する |
| 開発者 | 初期データの復元、接続設定、公開、障害調査を行う |

全閲覧者は一つの架空会社の同じデータを共有する。共通デモアカウントのため、記録上の社員と現実の閲覧者は一致せず、現実の人物の監査証跡にはならない。

## 3. 決定事項

- 日本語のWebアプリ。PC中心だがスマートフォンにもレスポンシブ対応する。
- Next.js、Neonのデータベース、Neon Authを使用する方針。
- 用意済みメールアドレス・パスワードで実際に認証する。管理者も用意する。
- 架空データのみを使用し、全員が同じ架空会社を共有する。
- 備品を1台ずつ管理する。項目は管理番号・名前・カテゴリ・説明。
- 本人が返却予定日を指定して、承認なしで貸出を登録する。
- 全社員が借り手・返却予定日・期限超過を閲覧できる。
- 本人の返却、管理者の代理返却、返却済み履歴の表示を行う。
- 備品登録・編集に加え、備品削除、貸出延長、社員管理をMVPに含める。
- メール送信機能は入れない。
- 初期管理者は権限変更・無効化・認証情報変更を禁止する。
- 備品約20点・同時利用約10人をデモ規模とする。
- 初期化は開発者用コマンドのみ。画面にはリセットボタンを設けない。
- 費用は無料枠内。Vercelを第一候補とし、条件が合わなければCloudflare Workersを検討する。有料契約は行わない。

## 4. レビュー対象の仮定

以下は細部を具体化するための提案であり、承認までは仮定とする。後続2文書の対応仕様にも適用する。

| ID | 仮定 |
|---|---|
| A-01 | 初期データは管理者1人・一般社員3人・備品20点。ログイン画面に共通デモ資格情報を表示する |
| A-02 | 貸出履歴は全有効社員が閲覧できる。氏名・備品名は貸出時点の表示用情報も残す |
| A-03 | 日付判定は日本時間。返却予定日当日は期限内、翌日0時から期限超過。貸出日は今日以降の予定日を指定する |
| A-04 | 1社員は複数備品を借りられる。1備品の未返却貸出は最大1件 |
| A-05 | 備品削除は論理削除。貸出中は削除不可。履歴と管理番号の一意性は維持し、復元画面は作らない |
| A-06 | 延長は本人・管理者が可能。新期限は旧期限より後、かつ今日以降。期限超過中も延長可能。変更前後・実行者・日時を履歴に残す |
| A-07 | 社員管理は追加・氏名と権限の編集・無効化まで。メールは作成時のみ設定。社員の物理削除・再有効化・パスワード変更画面は対象外 |
| A-08 | 追加社員は架空メールと初期パスワードを管理者が指定。自由な新規登録、確認メール、招待メール、メールでのパスワード再設定は無効 |
| A-09 | 無効化は貸出中でも可能。既存セッションも次の操作から拒否する。未返却備品は管理者が代理返却する |
| A-10 | 最後の有効管理者は降格・無効化できない。初期管理者は氏名も含め編集不可とし、デモ入口を維持する |
| A-11 | リアルタイム同期は不要。画面遷移・更新ボタン・操作成功後の再取得で最新状態を表示する |
| A-12 | デザインは白ベースの業務UI。状態を文字と色で示す。検索は備品名・管理番号、カテゴリと状態で絞り込む |

## 5. MVPの画面と利用シナリオ

| 画面 | 主な機能 | 対象 |
|---|---|---|
| ログイン | デモ資格情報表示、メール・パスワード認証 | 全閲覧者 |
| 備品一覧 | 検索・絞り込み、貸出状況、借りる | 有効社員 |
| 自分の貸出 | 未返却備品、期限、延長、返却 | 有効社員 |
| 貸出履歴 | 貸出・返却済み記録、延長履歴 | 有効社員 |
| 管理：備品 | 登録・編集・削除 | 管理者 |
| 管理：貸出 | 全未返却備品の延長・代理返却 | 管理者 |
| 管理：社員 | 追加・氏名と権限の編集・無効化 | 管理者 |

管理画面はタブにまとめてよい。貸出・延長・確認のために独立したページを増やす必要はない。

主要シナリオ:

1. 社員Aでログイン → 備品を検索 → 返却予定日を入力 → 貸出登録 → 自分の貸出を確認。
2. 別ブラウザの社員Bで一覧を更新 → Aの貸出が見える → 同じ備品は借りられない。
3. Aが期限を延長 → 延長履歴を確認 → 返却 → 備品が貸出可能になり返却履歴が残る。
4. 管理者が備品を追加・編集 → 返却済みの備品を削除 → 過去履歴は引き続き閲覧できる。
5. 管理者が架空社員を追加 → 新社員でログイン → 管理者が無効化 → 新社員の既存セッションも操作不可。
6. 管理者が期限超過・無効社員の未返却を確認し、代理返却する。

## 6. 保存データ・関係

| データ | 主な項目 | 関係 |
|---|---|---|
| 認証ユーザー | Neon AuthユーザーID、認証資格情報、セッション | 社員と1対1 |
| 社員 | ID、認証ユーザーID、氏名、メール、権限、有効状態、初期管理者保護フラグ、作成日時 | 貸出・延長操作の実行者 |
| 備品 | ID、管理番号、名前、カテゴリ、説明、削除日時、作成・更新日時 | 貸出と1対多 |
| 貸出 | ID、備品ID、借り手ID、貸出日時、返却予定日、返却日時、返却実行者ID、貸出時の備品・社員表示情報 | 延長記録と1対多 |
| 延長記録 | ID、貸出ID、旧期限、新期限、実行者ID、変更日時 | 貸出に所属 |

貸出状態は未返却貸出の有無と現在の日本日付から算出する。期限超過を別の固定フラグとして保持しない。認証パスワードはアプリの社員テーブルに保存しない。

## 7. 対象外

予約、承認、通知・メール送信、画像アップロード、CSV取込・出力、バーコード、部署、複数会社対応、チャット、AI機能、課金、リアルタイム配信、スマホ専用アプリ、詳細な分析ダッシュボード。

実在社員の招待や本番業務への転用も対象外。社員管理の入力には架空情報のみを求める。

## 9. 文書と実装の進め方

機能は02-functional-requirements.mdのFR-ID、品質条件は03-nonfunctional-requirements.mdのNFR-IDで追跡する。レビュー後にIssue一覧と依存関係を提示し、その合意後にGitHubへ登録する。

Orcaの並列開発では、データ定義・認証・権限・共通入出力の基盤を先に確定し、画面や業務機能を分担する。共有DBへのスキーマ変更は一人の担当に集約する。Issue分割・登録とアプリ実装は別工程であり、このドラフトは実装完了を意味しない。
